Case Study

Building editorial judgment into AI tools

I designed and built two AI prototypes: an information-architecture auditor and a copy critique tool. They tested how editorial standards could shape automated feedback. Both ran publicly before I retired them to limit cost and abuse.

Organization

Independent — rdrewj.com

Stack

Vercel serverless · Anthropic API · Upstash Redis · Cheerio

Role

Solo designer and developer

Status

Retired — public AI services disabled

What I owned: Product concept, interaction and content design, prompt architecture, deterministic scoring logic, front-end implementation, and server-side safeguards.

The premise

Applying content strategy to AI tools

I wanted to test whether tools could apply the same standards I use when auditing sites and editing copy.

That meant deciding what the model should judge, what code should calculate, and what evidence each recommendation needed.

The central design question was how to make automated criticism specific, proportionate, and grounded in the content.

The tools

An IA auditor and a copy clinic

CSX Audit crawled up to 10 pages, calculated information-architecture metrics, and used AI to identify content problems and recommend fixes.

Copy Clinic reviewed up to 1,500 characters of UX copy. It identified strengths and weaknesses, proposed a rewrite, and explained a broader content issue. I required the prompt to quote the submitted copy so the critique stayed specific.

Editorial decisions

Require evidence and calibrate severity

I instructed the audit to report fewer, lower-severity findings when the information architecture was sound. Each claimed content gap needed to trace to an unanswered question on a page or a clear expectation for that type of site. These were prompt requirements, not guarantees of model behavior.

I capped a site with no findings at 88: a ten-page crawl could not justify a perfect score. Repeated findings at the same severity had diminishing weight, so a recurring issue would not overwhelm the result. Both rules reflected editorial judgments about the limits of the audit.

Operational safeguards

Designing for public use

Public access also required limits on what the crawler could fetch and how much API usage it could generate.

Outcomes

What the prototypes demonstrated

2
Working AI tools designed, written, and shipped solo
4
Model calls orchestrated per audit, across two model tiers
Hybrid
Deterministic metrics combined with model-based analysis
4
Safeguards for URL fetching, usage, crawling, and unreadable content

I retired the public AI services to prevent ongoing API costs and abuse. The interfaces and source code remain available as project artifacts.

The most useful lesson was how much judgment sits inside an automated critique: what counts as evidence, how heavily to score a repeated issue, and when the tool has too little information to assess a page.

Sources and measurement

How outcomes were measured: The architecture and source code document what I built. This case study does not report a formal evaluation of model accuracy.
